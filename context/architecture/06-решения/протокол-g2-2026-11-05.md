Дата: 2026-11-05. Статус: локальные исправления и 122 автоматических теста выполнены; два разных настоящих Pinterest-аккаунта, взаимные отказы чтения, блокировка PMA и остановка после выхода из Pinterest A проверены живьём. ## Следующая ручная проверка

### Подтверждённый живой переход B → блокировка → A

Последнее испытание: пользователь сообщил о выходе из Pinterest A. В тестовом проекте уже был готовый run на 25 изображений, выполненный ранее, поэтому его нельзя использовать как доказательство реакции на выход. Агент создал новый обычный текстовый run после сообщения пользователя, без AI. Он остановился с сообщением о необходимости Pinterest-входа, 0 кандидатов и неизменным владельцем A. B не использовался.

Выявлен и исправлен дефект: `requireIdentity` выбрасывал обычный AppError, из-за чего остановка попадала в `error`, без кнопки продолжения. Теперь отсутствие/несовпадение username дают PinterestAccessError(login); worker сохраняет `blocked`, данные и owner. Добавлены проверки личности до и после каждой порции DOM-карточек, чтобы переключение внутри профиля не добавляло карточки другого аккаунта в checkpoint. Восстановление старых строго распознанных login-ошибок в `blocked` не запускает работу автоматически. Пять новых тестов покрыли выход/неверный аккаунт, явное продолжение с сохранением выбора, смену между порциями/во время чтения и точечную legacy-миграцию; полный итог 122 passed.

Сервис штатно остановлен через свой терминальный Ctrl+C и запущен с прежним разрешённым сетевым доступом. Этот новый live-run восстановлен в `blocked/login`, owner A, 0 картинок, AI off; прежний run с 25 картинками сохранён. Контрольная сумма экспортных доказательств не изменилась. Локальная PMA-сессия после перезапуска закрыта. Следующий ручной шаг: открыть A локальным паролем, войти обратно в Pinterest A и явно продолжить тот же заблокированный run; успешное восстановление живьём ещё не заявляется.

Пользователь завершил ручной вход B; сервис сохранил готовое подключение с username, отличным от исходного A. Во встроенном браузере под B отсутствовали проекты A. Через обычный UI создан только локальный проект «G2 — проверка изоляции B», без запуска поиска/AI/экспорта. Его API вернул собственный проект B и пустую историю. В той же авторизованной вкладке открыты заранее известные адреса A: project/export/upload/report ответили JSON «Нет доступа к проекту этого владельца», asset — «Изображение не найдено». Числовые HTTP-статусы этого браузерного инструмента не извлекались; доказательство — реальные отображённые тела ответов, а не обезличенный запрос без cookie.

Нажата штатная блокировка PMA: экран B очищен, его собственный project API теперь требует локального пароля. Отдельная проверка процессов нашла 0 Chrome-процессов с путём профиля B. Пользователь вручную вошёл локальным паролем A. Вернулись три прежних проекта A, тестового B среди них нет; по прямому URL B API снова отказал. A получил свою прежнюю квитанцию: Pinterest succeeded 7/7, Figma imported `30:2`, без повторного экспорта. Тот же A asset, закрытый для B, декодировался 235×215. В A-проекте доступны 10 версий истории и ручной выбор из семи. Открытие служебного Chrome A и кнопка «Я вошёл — проверить подключение» подтвердили исходную Pinterest-личность, а не B.

Для следующего испытания создан отдельный локальный проект «G2 — проверка сессии A», подготовлен текстовый запрос «общественный сад» без AI. Поиск ещё не запущен: пользователь должен сначала вручную выйти из Pinterest A, оставаясь в PMA под A. После его сообщения проверить остановку/сохранность owner, затем ручной вход и явное продолжение. Тестовые проекты сохраняются, очистка автоматически не выполнялась. Приватные ID и результаты — `.local/g2-live-plan.json` и `.local/g2-live-evidence.json`; паролей/cookie/кодов там нет.

Продолжение 2026-11-05: обнаружено, что прежний процесс ещё обслуживал порт 8787. Сверены его команда, принадлежность двух профилей каталогу этого проекта и совпадение ID подключений HTTP с локальной БД; активных поисков/экспортов/импортов не было. Остановлен только этот устаревший Node-процесс и запущен обновлённый `server/index.mjs`. До/после совпал SHA-256 упорядоченных записей selection/export/pinterest-export/figma-attempt/pin-save/export-recovery; экспортные доказательства не менялись. Это проверка сохранности локальных квитанций, внешние записи не выполнялись.

Две существующие записи подключения оказались одним и тем же Pinterest username; их число не доказывает второй аккаунт. Пользователь подтвердил, что другой настоящий аккаунт у него есть. Во встроенном браузере чата открыта форма нового подключения с именем «Проверка B»; пароль и ручной Pinterest-вход переданы владельцу. Пока B не подтверждён, проверку A→B не считать выполненной.

Native Computer Use не смог достоверно определить URL Chrome и остановил управление окнами; дальнейших native-вводов не было. Окна Chrome и ввод секретов не автоматизировались. Проверки HTTP продолжены независимо от native-инструмента.

Последующее подключение B остановилось до Pinterest-входа: журнал показал `page.goto: net::ERR_NETWORK_ACCESS_DENIED`. Процесс PMA, запущенный внутри ограниченного сетевого окружения, передал ограничение дочернему Chrome. Это не отказ пароля и не CAPTCHA. Пользователь успел создать две новые waiting-записи; ни одна ещё не содержит подтверждённой Pinterest-личности. Записи/пароли сохранены, автоматически ничего не удалялось.

Исправлена обработка: сбой открытия браузера после сохранения подключения возвращает его данные и безопасное предупреждение; UI сохраняет шаг входа и предлагает «Открыть Pinterest снова» в том же профиле. Регрессионный браузерный тест проверяет одну запись/один credential и тот же ID при повторе. Полный `npm test`: 117 passed, сборка прошла.

После проверки отсутствия активных jobs PMA перезапущен через разрешённый запуск с сетевым доступом. Отдельный чистый Chrome без пользовательского профиля открыл публичный Pinterest: HTTP 200. Контрольная сумма экспортных доказательств по-прежнему совпадает. Во встроенном браузере выбрано последнее сохранённое подключение «Мой Pinterest 2»; ожидается ввод владельцем его локального пароля, ручной вход B и проверка подключения. Публичный HTTP 200 не доказывает вход B или G2-изоляцию.

1. Владелец останавливает прежний процесс PMA, выполняет `npm run password`, выбирает своё сохранённое подключение и вводит новый отдельный пароль дважды. Пароль в чат/логи не переносится. Затем `npm start`; после перезапуска всё закрыто до пароля.
2. Открыть A паролем, убедиться в сохранности проектов/квитанций. Завершённые экспорты не запускать. Зафиксировать локально ID тестового A-проекта и адрес одного его media.
3. Через «Подключение Pinterest» создать B с отдельным паролем PMA. Вход Pinterest B выполняет владелец вручную в новом профиле. Проверка фиксирует ожидаемый username; заменить username уже связанного подключения нельзя.
4. В B проверить отсутствие проектов A и отказ известных API/media A. Открыть A только паролем A; старые задания и назначения сохраняют владельца. Для проверки остановки использовать отдельное новое тестовое задание, а не успешный экспорт этапа 7.
5. Заблокировать PMA; проверить пустой экран/отказ API/закрытие управляемых Chrome. Войти обратно. Отдельно вручную выйти из Pinterest A и проверить остановку нового поиска до получения/записи чужих данных. Истёкший/отозванный Pinterest-вход не переносит задачу в B.
6. Результаты живых действий дописать сюда. Пока этих свидетельств нет, галочку этапа 8 не ставить.
