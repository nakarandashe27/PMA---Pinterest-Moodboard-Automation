# Open-source решения для Pinterest: исследование 2026-11-03

## Вывод и решение для ближайшей версии

В просмотренных проектах не подтверждена готовая цепочка «текст/пример → ограниченный разнообразный черновик → выбор и замены → секретная доска проекта + редактируемый Figma-фрейм». Есть полезные загрузчики, клиенты неофициальных HTTP-ресурсов, расширения и небольшие мосты в Figma.

Для ближайшей версии выбираем небольшой собственный адаптер на Node.js и Playwright, используя уже проверенные нормализацию ссылок, извлечение DOM и загрузчик из G1. Это инженерный выбор по соответствию нашему сценарию и доступному окружению, а не утверждение, что собственный код надёжнее всех библиотек. Главный резервный кандидат для отдельного сравнения — pinterest-dl. Figma-плагин, работоспособность которого уже проверена, сохраняем.

## Как проверяли и чего проверка не доказывает

- Проверены метаданные 19 репозиториев, десять рассмотрены подробнее.
- Прочитаны 36 файлов на зафиксированных commit SHA: README, реализация, лицензии и документы/примеры тестов. Перечень, ссылки и blob SHA находятся в [evidence.json](evidence.json).
- Смотрели реальные способы поиска, привязку изображения к pin ID, авторизацию, запись в доску, ограничения циклов, устойчивость экспорта и побочные эффекты установки.
- Отдельно прочитаны сообщения о проблемах и комментарии. Закрытый старый issue не трактуется как действующая неисправность.
- Внешние проекты не устанавливались и не запускались. Их тесты здесь не выполнялись; наличие CI-файла не означает успешный текущий CI. Получение истории integration CI через коннектор оказалось недоступно.
- Предыдущие реальные проверки нашего G1 описаны в [практическом протоколе](../../context/architecture/06-решения/протокол-g1-2026-11-02.md). Они не являются тестом перечисленных библиотек.
- Метаданные поддержки — снимок на дату проверки. pushed_at включает изменения веток, поэтому для подробных кандидатов отдельно сохранён последний commit основной ветки. Число звёзд не использовалось как показатель правильности.

## Что обнаружено при чтении реализации

### pinterest-dl: сильный кандидат, но browser-режим требует проверки

На основной ветке просмотрен commit ab3914f; опубликованный release — 1.3.0 от 2026-06-15. В [endpoints.py](https://github.com/sean1832/pinterest-dl/blob/ab3914ff33ec800c952e40b8d73278c0621ccf74/pinterest_dl/api/endpoints.py) основной путь использует внутренние ресурсы сайта, а не официальный контракт API v5.

В [PlaywrightDriver](https://github.com/sean1832/pinterest-dl/blob/ab3914ff33ec800c952e40b8d73278c0621ccf74/pinterest_dl/webdriver/playwright_driver.py#L183) пин добавляется только внутри условия, что src содержит /236x/. В нашем G1 встречались другие реально отображённые размеры. Это конкретный повод для сравнительного теста: нельзя предполагать, что включение browser-режима сразу даст нужную подборку. Это вывод из кода, не воспроизведённый здесь баг.

Есть отдельные offline и live тесты. [Документ тестирования](https://github.com/sean1832/pinterest-dl/blob/ab3914ff33ec800c952e40b8d73278c0621ccf74/doc/TESTING.md) правильно различает проверки фиксированных данных и изменение внешнего API. Этот подход стоит перенести в наш проект.

### py3-pinterest: crop пина не равен внешнему Lens

Метод [visual_search](https://github.com/bstoilov/py3-pinterest/blob/fdbe3bc64e2ec5bf0e58da01be364d81b6ce689d/py3pin/Pinterest.py#L883) принимает данные существующего пина, его image_signature, размеры и координаты crop. Это подтверждает реализацию визуального поиска по пину, но не загрузку произвольного изображения заказчика.

В том же файле есть repin и создание доски с параметром privacy, по умолчанию public. Поэтому наличие метода create_board само по себе не обеспечивает наше требование SECRET. [Issue 225](https://github.com/bstoilov/py3-pinterest/issues/225), открытый на дату проверки, сообщает о несовпадающих полях входа. Это отдельный сигнал проверить авторизацию, а не доказательство неработоспособности всех функций.

### pin2figma: очень близкий мост, но другой контракт результата

В [extension/content.js](https://github.com/mujakkirhussen/pin2figma/blob/148cb62414bed5311fd847a52f8192eee8947bd4/extension/content.js#L55) вместе с изображением передаётся location.href. На странице поисковой выдачи это адрес поиска, а не конкретного выбранного пина. Для нашего требования «ссылка на источник у каждой карточки» такое поведение недостаточно.

В [server.py](https://github.com/mujakkirhussen/pin2figma/blob/148cb62414bed5311fd847a52f8192eee8947bd4/server/server.py#L62) выдача очереди сразу очищает её, без подтверждения создания объектов Figma. Проверка URL основана на вхождении строки pinimg.com, а CORS разрешает любые источники. Это основания не переносить мост в приложение без переработки. В [README](https://github.com/mujakkirhussen/pin2figma/blob/148cb62414bed5311fd847a52f8192eee8947bd4/README.md#L71) автор отдельно отмечает, что Windows-скрипты не проверены на Windows.

### pinrip: удобный CLI, но не наш формат данных

В [collectInPage](https://github.com/JaimeOrtegaxyz/pinrip/blob/61076288a1ccc1aa4742b31da70efbda4b217f5a/pinrip.js#L172) собираются URL изображений; связь каждого результата с конкретным pin ID не сохраняется в этой коллекции. Код также удаляет некоторые login/signup overlays. Наш адаптер должен сообщать о необходимости входа и останавливаться, сохраняя наблюдаемый интерфейс.

[package.json](https://github.com/JaimeOrtegaxyz/pinrip/blob/61076288a1ccc1aa4742b31da70efbda4b217f5a/package.json#L9) содержит postinstall для установки агентного skill. README описывает чтение cookies обычного браузера. Эти действия не нужны нашему приложению. Нам нужен собственный изолированный профиль и ручной вход.

### Search by Image: существование функции не доказывает стабильность endpoint

В [searchPinterest](https://github.com/dessant/search-by-image/blob/d5d20a64be2fc0fccdedbf52becb0a5f80a83848/src/utils/engines.js#L228) действительно отправляется внешний файл в v3 visual_search/extension/image. Но это не документированный Lens API v5.

В [issue 350](https://github.com/dessant/search-by-image/issues/350) описан сбой в январе 2025; затем пользователи сообщили о восстановлении в апреле, issue закрыт. Нельзя ни объявлять endpoint навсегда неработающим по старому сообщению, ни считать его проверенным сегодня по сохранившемуся коду. Наш рабочий нативный UI-путь Lens из G1 остаётся отдельным доказательством.

### LocalBoard, gallery-dl и простой веб-прототип

[LocalBoard](https://github.com/thetejasagrawal/Pinterest-LocalBoard/blob/e7b35b0389868b717ad0817b77540052de0e7bfd/README.md) полезен как пример выбора, отмены и восстановления экспорта. Его [content script](https://github.com/thetejasagrawal/Pinterest-LocalBoard/blob/e7b35b0389868b717ad0817b77540052de0e7bfd/extension/content.js) также читает внутренние initial props: это не чисто DOM-решение.

В [Pinterest extractor gallery-dl](https://github.com/mikf/gallery-dl/blob/811d917b4973ae4f556a760e289784fd4714e2f1/gallery_dl/extractor/pinterest.py) есть отдельные search и related extractors. Большая поддерживаемая кодовая база полезна, но не снимает необходимость проверять соответствие источников и фактическое число файлов. Старые закрытые жалобы на неполную выгрузку не объявляются текущим дефектом релиза.

[pin_scraper.py](https://github.com/workordie/pinterest-scraper/blob/42ed7306e44b6d9fd9d2d53d238537ab08e56ced/pin_scraper.py) сохраняет pin_url из ссылки карточки, что ближе к нашему контракту. Однако готового слоя аккаунтов, отбора и надёжных экспортов нет.

## Что действительно даёт официальный API

[Search API](https://github.com/pinterest/pinterest-python-generated-api-client/blob/main/docs/SearchApi.md) различает поиск пинов пользователя и partner search; последний описан как beta, доступная не всем приложениям, с выдачей top 10. Это не основание обещать всем аккаунтам тот же поиск, что на сайте, или Lens.

[Save Pin](https://github.com/pinterest/pinterest-python-generated-api-client/blob/main/docs/PinsApi.md#pins_save) документирует сохранение существующего публичного pin ID в доску операционного пользователя. Create Pin не подменяет эту операцию. Поиск, сохранение и нужные права надо выбирать и проверять раздельно.

Открытая лицензия библиотеки не выдаёт разрешение на Pinterest и не передаёт права на изображения. [Действующие условия Pinterest](https://policy.pinterest.com/en/terms-of-service) ограничивают неразрешённый автоматизированный доступ; на странице отдельно анонсировано обновление с 2026-11-12. Наличие logged-in браузера или платного посредника само по себе не закрывает этот вопрос. До постоянной эксплуатации нужно подтвердить допустимый способ доступа; технический прототип это не доказывает. Ограничение доступа не маскируем задержками, stealth или удалением форм входа.

## Конструкция первой веб-версии

Собственный небольшой слой нужен не ради переписывания загрузчиков. Он хранит контракт нашего продукта:

1. Связь source pin ID → каноническая ссылка → реально наблюдённое изображение → локальный файл.
2. Отдельный проект, задание, результаты поиска и выбранный набор.
3. Конечные лимиты количества/времени, отмену и честное отображение недобора.
4. Изолированные browser profiles, ручной вход; без чтения cookies обычного браузера и глобальных установочных скриптов.
5. Остановку при необходимости входа или ограничении Pinterest, без обхода.
6. Один выбранный набор для двух экспортов и раздельные подтверждения результата.
7. Сохранение нового savedPinId отдельно от sourcePinId — это уже обнаружено в нашем G1.

[Документация Playwright](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context) позволяет отдельный persistent context. Его состояние защищаем как учётные данные, согласно [руководству по авторизации](https://playwright.dev/docs/auth).

Сначала собираем веб-каркас и сохраняем реальные результаты. Внешний Lens, качество AI-отбора и массовое сохранение не объявляем завершёнными из-за появления кнопок. Выбор AI-провайдера и лимита расходов остаётся отдельным последующим шагом.

## Проверка выбранного решения перед пилотом

Для ограниченной сравнительной проверки: один текстовый запрос о МАФ, один об азиатском саде, один с бионическими формами; затем существующий пин и внешний JPG Lens. Цель — проверить механизмы, а не собрать большую базу.

Для каждой попытки фиксировать: версию адаптера и аккаунт без секретов, время, наблюдённые pin IDs, уникальные локальные файлы, число ошибок, соответствие исходных ссылок и причину остановки. Проверить перезапуск, истёкший вход, отмену и один неудачный download. Пределы количества/времени задаются в коде и не повышаются автоматически.

Если сравнивать pinterest-dl с нашим DOM-путём: запускать отдельно с фиксированной версией, ограниченным запросом и явным выбором API/browser режима; не использовать общий критерий «команда завершилась». Проверять pin→image соответствие, а не только количество JPG.

Качество и время ручного отбора сравниваем на реальных заданиях архитектора после появления рабочей цепочки. Новых обещаний по точности и скорости этот обзор не даёт.
